# 诊断驱动的结构化属性测试修复：开发协议

## 研究目的

上一版模型结构化修复能够生成并审计部分 JSON DSL 工件，但在固定随机种子和固定容器镜像的配对评估中没有带来直接的严格 F-to-P 增益。其主要行为是扩展原始值域，而不是构造状态转换或操作序列。本协议检验一个更严格的工程假设：先要求模型以受限 JSON 描述公开材料可支持的覆盖缺口，再要求其输出与该诊断一致的结构化编辑，观察这一约束能否提高合规工件的质量。

本协议只用于开发集验证。`BIDC-003`、`CACH-005` 与 `CTRS-001` 均已在前序实验中用于分析或人工修复，因此不承担未见任务泛化评估。

## 输入隔离

每个模型调用只能读取以下材料：

- 经提示词过滤的冻结 `pbt_test.py`；
- 任务目录中的公开文档与既有测试；
- 由冻结 baseline AST 机械提取的 `@given` 参数 selector 清单；
- JSON schema 与结构化编辑 DSL 的公开规则。

模型不可访问 ground truth、补丁、fixed diff、评估器输出、文件写入工具或人工诊断测试。提示词过滤器会删除含有 `bug`、`trigger`、`injected` 等结果提示词的注释和 docstring。诊断 rationale 也不得出现缺陷触发条件、ground truth、补丁、评估或断言结果等语言。

## 两阶段协议

### 第一阶段：覆盖诊断

模型只能返回一个 JSON 对象，字段为任务标识、已有目标测试、覆盖缺口类别、简短依据和所需操作。覆盖缺口限定为以下四类之一：

1. `state_transition`；
2. `operation_sequence`；
3. `configuration_combination`；
4. `boundary_value`。

状态转换与操作序列诊断至少列出两个受限操作词：构造、配置、更新、移除、清空、复制、查询、观察、序列化或反序列化。JSON schema、目标测试名和禁用结果语言由程序验证。每个任务最多尝试两次；失败反馈只包含 schema 或 AST 拒绝原因，不包含运行或 F-to-P 结果。

### 第二阶段：受诊断约束的 DSL

只有第一阶段得到有效诊断时才调用第二阶段。模型仍只返回 JSON DSL，随后由确定性 AST 变换器应用。所有既有测试函数、断言和 import 必须保留；禁止修改断言、添加控制流、异常处理、文件操作、动态导入或危险调用。

- 对 `state_transition` 与 `operation_sequence`，DSL 必须克隆诊断指向的既有测试，并包含插入语句或赋值替换；仅 `extend_given` 不通过一致性审计；
- 对 `configuration_combination`，DSL 必须克隆诊断指向的测试，并包含赋值替换；
- `boundary_value` 可以使用 `extend_given` 或 `add_examples`，但仍须通过 no-op 和 AST 审计。

第二阶段最多尝试两次，且不接收评估反馈。任何输出格式错误、schema 违规、诊断-DSL 不一致、AST 违规或语义 no-op 均计为该任务未接受工件，并按意向性计入分母。

## 开发任务与评估计划

模型固定为 `openai/qwen3-coder-plus`，`temperature=0.0`；每阶段最多两次尝试、最多四项编辑。先在三个开发任务生成工件：`BIDC-003`、`CACH-005`、`CTRS-001`。

仅对静态审计接受的工件进行动态评估。评估与未修改的冻结 baseline 成对运行，使用相同的 Hypothesis seed、相同的显式容器镜像和相同的评估参数。主要指标为严格 F-to-P；宽松发现和运行遥测不作为方法结论。原始输出保存在评测输出目录，研究记录只写入可复核的摘要、配置指纹和结果解释。

## 预先定义的判定标准

进入未见任务评估需要同时满足：

1. 三个开发任务均生成通过静态审计的工件；
2. 至少一个模型工件相对冻结 baseline 产生可直接归因的严格 F-to-P 增益；
3. 增益在多个预先冻结的随机种子下可重复；
4. 模型、提示词、容器镜像和评估参数全部锁定。

若条件未同时满足，结果仅解释为该协议版本在开发集上的方法验证结果。

## 协议版本结果

### 版本 1

`BIDC-003` 的诊断阶段第一次调用即通过 schema。第二阶段连续两次返回同一 DSL：`insert_before.statements` 包含空字符串，`insert_at_start` 包含 `if ...: return`。前者违反非空字符串规则，后者属于新增控制流和提前返回，因此工件未接受，未进入动态评估。

该版本暴露了 DSL 字段局部格式约束表述不清的问题。原始输出保留于评测输出目录。

### 版本 2

版本 2 在第二阶段提示词中补充了 DSL 字段说明。`BIDC-003` 的第二阶段通过；`CACH-005` 和 `CTRS-001` 的诊断通过但 DSL 均未通过，分别出现 `lambda` 和函数定义。BIDC 工件与 baseline 的固定 seed 配对复评已完成，严格 F-to-P 均为 `0/4`。

### 版本 3

版本 3 保留版本 2 的 schema、AST 审计、模型、任务、尝试次数和评估条件，并在第二阶段加入不依赖任务 ground truth 的最小合法 JSON/代码形状示例，明确直接赋值和方法调用是可接受形式，回调、lambda、辅助函数、注释和控制流均不接受。

三个任务的诊断均通过；只有 BIDC 的 DSL 通过。BIDC 的配对复评严格 F-to-P 仍为 `0/4`，新增测试在 buggy 和 fixed 版本中均失败。CACH 与 CTRS 没有合规工件，未进入动态评估。
